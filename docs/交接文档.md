## 一、项目定位与技术栈

面向 OKX 永续合约的**本地桌面行情分析工具**：轮询行情、计算五维评分与方向信号、记录用户手工订单、展示市场状态，并开始积累「带方向的预测记录」用于后续回验。

它**不是**交易机器人：不挂单、不下单、不管理交易所仓位，所有订单都是用户手工记账。

| 层 | 实现 |
|---|---|
| 语言/运行时 | Python 3.10.11（venv 在 `.venv`） |
| 后端 | FastAPI 0.95.2 + uvicorn + APScheduler（后台线程调度） |
| HTTP 客户端 | requests + certifi 显式 CA；走 `HTTP_PROXY`/`HTTPS_PROXY` |
| 前端 | 原生 HTML + CSS + ES Module JS，无构建步骤、无框架、无 npm |
| 桌面壳 | pywebview 6.2.1（WebView2）+ pystray 托盘图标 |
| 存储 | SQLite（`backend/data/*.db`）+ JSON（`watchlist.json`） |
| 打包 | PyInstaller 6.21.0（`backend/OKEworkplace.spec`） |

## 三、进程模型与启动方式

**单进程 + 双线程**：主线程跑 pywebview 窗口与托盘；后台线程跑 uvicorn；APScheduler 在 uvicorn 进程内以 interval 任务刷新行情。

启动流程（`backend/entry_exe.py`）：

1. 从 8000–8019 依次探测空闲端口；
2. 后台线程启动 uvicorn（`127.0.0.1:<port>`，`log_config=None`）；
3. `_wait_for_server` 用 `urllib` + `ProxyHandler({})` **强制直连**轮询 `/health`（`.env` 里的代理会把 127.0.0.1 也劫持，必须绕过）；
4. 打开窗口，标题为 `OKEworkplace v<VERSION> - 交易分析终端`；
5. 关闭窗口 → 前端 `beforeunload` 发 `POST /api/shutdown` → 后端 `SIGINT` 优雅退出、释放端口。

开发模式启动（当前日常使用）：

```bat
cd d:\OKEworkplace
.venv\Scripts\python.exe backend\entry_exe.py
```

- 非 frozen 时 URL 附加 `?dev=1`，启用两项开发设施：
  - 后端注册 `GET /dev/frontend-version`（遍历 `frontend/` 取最大 mtime）；
  - 前端每 1500ms 比对版本号，变化则 `location.reload()`；同时支持 F5 / Ctrl+R。
  - reload 前设置 `window.__okeReloading`，`beforeunload` 据此跳过退出信标，避免刷新把后端一起关掉。
- 打包版没有 `?dev=1`，上述接口与轮询均不生效（零开销）。

仅后端（无窗口）调试：在 `backend` 目录执行
`.venv\Scripts\python.exe -m uvicorn app.main:app --host 127.0.0.1 --port 8000`。

注意事项：

- 窗口关闭会终止后端；用浏览器打开页面时关闭标签页同样会触发退出信标。
- 通过 shell 的 `Start-Process` 启动可能随终端会话回收，稳定做法是用资源管理器/计划任务拉起 `pythonw`。
- 进程未做单实例互斥：再启动一个实例会自动占用 8001。

## 四、数据流

```
APScheduler（每 5s, max_instances=3）
  └─ market_service.refresh_all()
       └─ 每个币种：8 个 OKX 接口并行（16 线程池）
            ticker / candles(100根) / open_interest / funding_rate
            mark_price / index_price / trades / books
       └─ signal_engine.evaluate()
            指标：EMA20/60/120、RSI14、MACD、ATR14、OI 变化、资金费率、CVD
            └─ calculate_market_score() 五维加权 → analysis
                 direction / score / level / risk / reasons / components
       └─ DirectionTracker.feed() 稳定方向
            raw_direction 保留原始方向，direction 为过滤后方向，
            direction_changed 标记本次是否发生方向确认变更
       └─ 写入内存缓存 _latest_prices / _latest_signals_cache
       └─ SignalDB.save_signal()             → signals.db: signals
       └─ prediction_logger.maybe_log()      → signals.db: predictions（带节流）
前端口径（每秒刷新）：
  GET /api/monitor/snapshot → 渲染概览卡片
  GET /network/status       → 顶部数据源徽标与提示条
  GET /api/analysis/{sym}   → 每 2s 拉一次，供评分卡/信号卡使用
  GET /api/v2.3/orders + /api/v2.3/price-levels/check → 订单页
```

关键事实：

- 所有「实时」都来自轮询，**没有 WebSocket / SSE**。
- 前端每秒重绘卡片（`innerHTML` 赋值），不做虚拟 DOM。
- 信号是本地规则引擎的产物，不来自交易所或第三方。

## 五、数据存储

### 5.1 `signals.db`（开发：`backend/data/`；打包：exe 同目录）

| 表 | 内容 | 写入频率 |
|---|---|---|
| `signals` | 判断记录：方向、过滤方向、评分、等级、风险、价格（`raw_signal` 对新行留空） | 方向/等级/风险变化、评分变化 ≥5，或每 5 分钟兜底 |
| `signal_snapshots` | 原始行情快照（K 线/逐笔/盘口），zlib 压缩后存 BLOB | 过滤后方向变化时，或每 5 分钟一份 |
| `analysis_snapshots` | 五维分项与趋势阶段 | 目前无调用方写入 |
| `predictions` | 有方向判断的留档（见 8.6） | 方向变化或 ≥30 分钟一条 |
| `prediction_results` | Future Validator 回验结果（见 8.7），`UNIQUE(prediction_id, horizon)` | 到期后每个 horizon 一条 |

**写入策略（2026-11-20 改造）**：不再每 5 秒存 38KB 全量快照。判断记录与原始快照分离：
- `signals` 仅存判断字段，触发条件为方向/等级/风险变化、评分变化 ≥ `OKE_SIGNAL_SCORE_DELTA`（默认 5），
  或距上次写入 ≥ `OKE_SIGNAL_HEARTBEAT_MINUTES`（默认 5 分钟）；
- `signal_snapshots` 存压缩快照（`zlib+json`，实测压缩率约 10.3%），按 `OKE_RAW_SNAPSHOT_MINUTES`（默认 5 分钟）降采样，
  过滤后的方向变化时额外留一份；`raw_direction` 逐跳抖动，不参与触发。
- `signals` 与 `signal_snapshots` 均有 `created_at` 索引，保留策略同时清理两张表。

**实测效果**：改造前 36 行/分钟、38.5KB/行（≈2GB/天）；改造后 24.9 行/分钟、单行平均 52B，快照 3,969B/条、约 3 条/5 分钟，
折算约 **5–6MB/天**（降幅约 99.7%）。写入耗时 8.12ms → 8.11ms/次。旧的大行会在 7 天保留期内逐步清理。

**保留策略**：`OKE_SIGNAL_RETENTION_DAYS`（默认 7 天），`prune_signals` 每
`OKE_SIGNAL_CLEANUP_INTERVAL_MINUTES`（默认 60 分钟）执行，首跑启动后 60 秒；按
`OKE_SIGNAL_CLEANUP_BATCH_SIZE`（默认 500）分批删除并让出写锁。结果见 `GET /api/v3/maintenance/signals`。

**并发与迁移**：`signals.db` 启用 WAL + `busy_timeout=5000` + `synchronous=NORMAL`；新增表均为
`CREATE TABLE IF NOT EXISTS`，`predictions` 新字段用 `ALTER TABLE ADD COLUMN`，旧库无需删除。

### 5.2 `user_trades.db`

| 表 | 内容 |
|---|---|
| `orders` | 手工持仓：symbol / direction / entry_price / quantity / note / status |
| `closed_orders` | 平仓历史：close_price、pnl_pct、pnl_abs、result、时间 |

### 5.3 其他

- `backend/watchlist.json`：关注币种与周期（当前 BTC/ETH/SNDK，15m），增删币种即时保存。
- `.env`：`HTTP_PROXY` / `HTTPS_PROXY`、OKX 基础地址与密钥、`POLL_INTERVAL_SECONDS`、方向滤波参数、网络与预测阈值。
- 内存态（重启即丢）：告警环形缓冲、价格触及 30 分钟冷却、`DirectionTracker` 缓冲、市场状态阈值外的状态。

### 5.4 自动备份与恢复

- 策略：`signals.db` 与 `user_trades.db` 每 `OKE_BACKUP_INTERVAL_HOURS`（默认 24 小时）自动备份，
  首跑在启动后 5 分钟；备份目录默认 `backend/data/backups/`（可用 `OKE_BACKUP_DIR` 覆盖），
  按前缀保留最近 `OKE_BACKUP_KEEP`（默认 7）份。
- 实现：SQLite 在线备份 API（`Connection.backup`），不阻塞行情写入；文件名 `signals_<UTC时间戳>.db`、
  `user_trades_<UTC时间戳>.db`。状态见 `GET /api/v3/maintenance/backup`。
- 恢复步骤（手工，需短暂停机）：
  1. 关闭程序；
  2. 把 `backups/signals_<时间戳>.db` 复制为 `backend/data/signals.db`，同时删除同目录 `signals.db-wal`、`signals.db-shm`；
  3. 如需恢复订单，同样处理 `user_trades.db`；
  4. 启动后检查 `/health`、`/api/v3/maintenance/signals` 与行数；
  5. 数据量大时再执行一次 `VACUUM` 回收空间。
- 演练记录（2026-11-20）：停机 → 备份 → 复制回临时目录 → `PRAGMA integrity_check=ok`，
  `signals` 5,970 行 / `signal_snapshots` 218 行 / `predictions` 6 行 / `user_trades.orders` 2 行、
  `closed_orders` 8 行与源库逐项一致。

## 六、版本与发布约定

- **版本单一真源**：仓库根 `VERSION`（当前 `2.3.0.0`）。`backend/app/core/config.py` 启动时读取；冻结包读 `_internal/VERSION`。`/health`、窗口标题、PyInstaller 产物命名、前端角标全部跟随，禁止在代码里另写版本号。
- **发布目录**：`dist\current\` 只保留当前正式版；旧版本进 `dist\archive\`，不作为启动入口。
- **打包**：PyInstaller 使用 `backend/OKEworkplace.spec`（onedir，产物名 `OKEworkplace_v<版本>.exe`）。发布时旧产物移入 `dist\archive\`，新产物覆盖 `dist\current\`；打包版数据文件（`signals.db`、`user_trades.db`、`watchlist.json`）位于 exe 同目录。
- **发布流程（2026-11-20 起）**：日常改动只在开发环境验证 → 用户明确「审查通过、可以封包」→ 才允许打包覆盖 `dist\current`。禁止顺手改 `VERSION`、禁止未确认推送。

## 八、已实现能力边界

### 8.1 五维评分与信号

- 维度与权重：趋势 30 / 动量 20 / 成交量 20 / OI 20 / 资金费率 10，合计 100。
- 输出 `score`、`level`（强烈关注 / 重点关注 / 观察 / 中性 / 放弃）、`direction`（LONG/SHORT/NEUTRAL）、`risk`、`reasons`。
- 只做规则打分，不训练模型；权重目前固定，没有在线优化。

### 8.2 方向滤波（v2.2）

- 参数：缓冲 12、滞回 35/55、确认 3 次、翻转 4 次、冷却 5 分钟（均可用环境变量覆盖）。
- 输出稳定方向，同时保留 `raw_direction` 和 `direction_changed`，前端用徽标区分。
- 属于启发式平滑，没有历史回测证明其在各市场状态下都更优。

### 8.3 Market Regime

- 纯规则四分类：BULL / BEAR / RANGE / HIGH_VOLATILITY，另有 UNKNOWN。
- 先用 ATR14/价格 ≥ 2.5% 判高波动；再用 EMA20/60/120 排列与分离度（≥0.3%）判牛熊，其余为震荡。
- OKX 默认只返回 100 根 K 线，EMA120 长期缺失 → 实际多数走「双均线降级」路径，原因文案会说明。
- 价格跳变守卫：收盘价与 EMA20 偏离 >50% 时判 UNKNOWN（例如 SNDK-USDT 由 787 跌到 87，指标整体失真），不再输出误导性的「高波动」。
- 阈值可环境变量覆盖；不参与评分，只作展示与后续语境。

### 8.4 价格触及提示（v2.3）

- 仅针对**用户手工订单**：现价进入开仓价 ±0.5% 时，结合当前系统方向给出「建议持有 / 考虑平仓 / 信号未就绪」。
- 冷却：同一订单 + 同一建议 30 分钟内只提示一次（内存态，平仓时清理，重启后重置）。
- 只做提示，不自动平仓，不计算止盈止损。

### 8.5 网络状态与顶部提示

- 不做主动探测，按「最近一次成功取数时间」推导：数据年龄 ≤15s 视为可用（`OKE_DATA_GRACE_SECONDS`）。
- 前端提示两段式：启动判定一次（不可用则提示，带代理 host:port）；之后仅数据超过 60s 无更新（`OKE_DATA_STALE_SECONDS`）提示一次；单次抖动完全静默。
- 代理端口来自 `HTTP_PROXY`，不写死。

### 8.6 Prediction Logger

- 触发：`direction` 为 LONG/SHORT 时尝试落库；NEUTRAL 不记录。
- 节流：**方向变化立即记录；方向不变时距上一条 ≥30 分钟才再记**（`OKE_PREDICTION_MIN_INTERVAL_MINUTES`，节流状态以数据库最后一条为准，重启不丢）。
- 字段：`created_at`、`symbol`、`direction`、`score`、`level`、`regime`、`price`、`reasons`（JSON，最多 5 条）、
  `timeframe`、`price_type`、`strategy_version`、`verifiable`。
- **时间口径**：全项目统一 ISO 8601 UTC 字符串（带 `+00:00`）。
- **价格口径**：统一为 `price_type=candle_close`，入场价取预测时最后一根**已收盘** K 线的 close，与回验完全一致。
- 历史记录（本次迁移前的 3 条）缺少 `timeframe/price_type`，已置 `verifiable=0` 并写明原因，不回填猜测值。
- 查询：`GET /api/predictions`。

### 8.7 Future Validator（回验闭环）

- 触发：APScheduler 每 60 秒扫描（`OKE_VERIFY_INTERVAL_SECONDS`），首跑提前到启动后约 30 秒，等价于启动补算。
- 单实例：数据目录下 `validator.lock` 互斥，锁超过 10 分钟视为残留自动接管；重复运行由 `UNIQUE(prediction_id, horizon)` + `INSERT OR IGNORE` 兜底。
- 周期：30m / 1h / 4h 三个 horizon 各自独立到期、各自一行结果。
- 结果状态机：
  - `verified`：数据完整并完成计算；
  - `insufficient_data`：K 线窗口未覆盖、缺口超限（OKX 只有 100 根，停机过久补不齐），**不计为亏损**；
  - `invalid`：价格跳变（如 SNDK 类合约重定价）或价格异常，隔离且不计入统计；
  - `failed`：取数/计算异常，保留记录，10 分钟后自动重试；
  - `pending`：未到期，不写结果。
- 指标：`entry_price`、`exit_price`、`gross_return`、`estimated_cost`（双边手续费 + 滑点，默认 0.14%）、
  `net_return`、`mfe`、`mae`、`outcome`（`net_return` 超过 `±OKE_VERIFY_FLAT_THRESHOLD_PCT` 才判 WIN/LOSS，其余 FLAT）。
- 结果查询：`GET /api/v3/predictions/results`；最近一次执行：`GET /api/v3/verify/status`。
- 存储改造后回归（2026-11-20）：新预测均带 `timeframe=15m`、`price_type=candle_close`；
  实测入场价与预测记录完全一致（61770.6），30m 回验产出 `verified/LOSS`，再次扫描不重复写入。
- 未做：命中率汇总、Dashboard、按币种/权重分析、失败告警。

### 8.8 订单记账

- 本地手工开平仓，盈亏按方向与数量计算；`orders` 与 `closed_orders` 两张表。
- 不连接交易所下单接口，不读取交易所真实持仓。

### 8.9 资金行为分析（半停用）

- `model/capital_behavior.py` 仍在仓库中，但 `/api/analysis/{symbol}` 固定返回
  `{type: "unavailable", available: false, reason: "缺少真实买卖量数据，资金行为暂不可用"}`。
- 原因：此前用 0 买卖量强行计算，结论恒为「数据模糊」，属于误导，已主动停用，等待真实逐笔买卖数据源。

### 8.10 告警

- 进程内环形缓冲（最多 200 条），去重键 `symbol:direction:score//5*5`，冷却 2 分钟。
- 只随 `/api/monitor/snapshot`、`/api/monitor/alerts` 返回，不落库、不推送系统通知。

### 8.11 前端

- 六个 Tab：概览、评分分析、交易信号、订单、绩效、币种列表。
- 每秒刷新快照；分析每 2 秒按币种拉取；全部原生 JS 渲染。
- 开发模式支持文件变更自动刷新与 F5/Ctrl+R。
- 顶部提示条从页面顶部滑入，5 秒自动收起。

### 8.12 绩效 Dashboard（最小版）

- 位置：第 5 个 Tab「绩效」，打开时立即拉取，之后每 30 秒刷新。
- 内容：6 个汇总卡片（预测总数、已回验、待回验、胜率、方向准确率、平均净收益）、
  按币种与按周期两张表、最近 30 条回验明细；有效样本 <30 时显示"样本不足"提示。
- 口径：胜率 = WIN / 已回验；方向准确率 = WIN / (WIN+LOSS)；净收益已扣双边手续费与滑点。
- 未做：图表、按评分/regime 分层、权重趋势、导出；这些等有效样本足够后再评估。

## 九、已知限制与硬约束

外部规划新功能前，请先按这一节判断可行性。

### 9.1 网络与数据源

- **必须使用代理**：本机 DNS 被污染，直连 OKX 不可用；所有对外请求走 `HTTP_PROXY`/`HTTPS_PROXY`（当前 `127.0.0.1:12334`）。
- 本机自检（如入口等待 `/health`）必须显式直连，否则会被代理劫持导致 30 秒超时。
- 代理存在长尾：单次请求 4–6 秒的超时偶发出现，因此任何「实时探测」都不能直接决定可用状态。
- OKX K 线窗口固定 100 根 → 120 周期 EMA 长期不可用；新上市/发生重定价的合约会让指标失真。
- 轮询成本：3 个币种 × 8 个接口 / 5 秒 ≈ 24 请求/5 秒，扩展币种要同步评估限频与线程池（单币种 10 线程 + 抓取 16 线程）。

### 9.2 安全与部署形态

- **接口最小加固（2026-11-24）**：Host 只允许 `127.0.0.1/localhost/::1`，带 Origin 的请求同样校验；
  CORS 只允许本机源。桌面壳每次启动生成一次性 token 并通过页面 URL 注入，所有非 GET 请求需带
  `X-OKE-Token`（或 `token` 查询参数）。直接 `uvicorn` 运行时不注入 token，写接口不额外拦截，但受 Host/Origin 限制。
- `POST /api/shutdown` 在桌面壳下默认开启，直接用 `uvicorn` 运行时默认关闭（`OKE_ENABLE_SHUTDOWN` 可显式覆盖），且需要本地 token。
- 桌面壳与 Web 部署差异：
  - 桌面：pywebview 窗口、托盘、关闭即退出、`beforeunload` 发退出信标；
  - Web：无窗口/托盘，关闭标签页会误杀后端，必须去掉该信标并改成常驻服务。
- 未做多用户、未做权限，SQLite 是单机单写者模型。

### 9.3 存储与进程

- SQLite 无迁移框架，只能靠 `CREATE TABLE IF NOT EXISTS` / `ALTER TABLE ADD COLUMN` 增量兼容；改约束仍需重建表。
- `signals` 已接入保留策略（默认 7 天、分批删除、每小时一次），并改为"判断记录 + 压缩快照降采样"，
  新数据约 5–6MB/天；历史大行会在保留期内清理。删除不会自动缩小文件，回收磁盘需手工 `VACUUM`。
- 告警、价格冷却等是内存态，重启丢失；回验任务用 `validator.lock` 互斥，锁文件残留超过 10 分钟会被接管。
- 无单实例互斥，重复启动会占用下一个端口（8001…）。
- SQLite 已启用 WAL + `busy_timeout=5000`，并发读写压测（行情写入 + 清理 + 回验 + 备份同时跑 30 秒）无 `database is locked`；
  但备份瞬间可能带来约 0.8 秒的写延迟抖动，属可接受范围。
- 所有业务逻辑同步执行在 FastAPI 线程池中，长任务（如大库 VACUUM、全量备份）会拖慢接口。

### 9.4 实时性

- 只支持轮询：后端 5 秒、前端 1 秒；**没有 WebSocket/SSE**，也没有推送通知。
- 前端每秒整体重绘，数据量大时会明显掉帧，不适合高密度盘口展示。

### 9.5 分析能力

- 评分、方向、市场状态都是规则/启发式，没有回测报告与命中率统计；Prediction Logger 刚开始积累数据，暂时无法证明有效性。
- 单一周期（每个币种一个 timeframe，当前 15m），没有多周期共振。
- 资金行为已停用；没有订单簿深度建模、没有盘口微观结构分析。

## 十一、接手检查清单

1. 确认代理：`Test-NetConnection 127.0.0.1 12334`（端口以 `.env` 为准）。
2. 确认 8000–8019 无占用（`netstat -ano | findstr :800`）。
3. 启动开发版：`.venv\Scripts\python.exe backend\entry_exe.py`，窗口标题应含 `v2.3.0.0`。
4. 基础自检：

```bash
curl http://127.0.0.1:8000/health
curl http://127.0.0.1:8000/network/status          # data_source=REAL, data_age_seconds 很小
curl http://127.0.0.1:8000/api/monitor/snapshot    # prices / signals 非空
curl http://127.0.0.1:8000/api/market-regime/BTC-USDT
curl http://127.0.0.1:8000/api/predictions?limit=5
```

5. 改前端后无需重启（开发模式 1.5 秒内自动刷新）；改后端需重启进程。
6. 动手前按约定备份到 `代码备份\v_时间戳_说明\`；不打包、不改 `VERSION`、不推送，除非用户明确要求。
