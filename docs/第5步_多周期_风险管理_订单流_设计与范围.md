## 0. 结论速览

| 功能 | 解决什么问题 | 主要数据源 | 是否新增外部依赖 | 建议顺序 | 粗略工作量（单人） |
|---|---|---|---|---|---|
| 风险管理 | 手工订单没有止损/止盈、没有仓位风险与组合敞口，无法回答“这笔最多亏多少” | 本地 `user_trades.db` + 内存最新价，不新增外部请求 | 无 | 第 1 | 2.5–3 人日 |
| 多周期 | 单一 15m 周期会把“逆大周期”的信号也标成做多/做空，缺少趋势语境 | OKX REST K 线（3 个周期，60s 级刷新） | 无 | 第 2 | 2–2.5 人日 |
| 订单流 | 现有 CVD 只是最近一批成交的快照求和，无法回答“谁在主动成交、盘口偏向哪边” | OKX REST 逐笔成交 + 盘口（5–10s 级采样） | 无（WebSocket 方案另计） | 第 3 | 3.5–4 人日 |
| 预测上下文 | 新指标目前无法回答“多周期共振/订单流是否真的提高命中率” | 上述三者缓存的快照 | 无 | 第 4 | 1–1.5 人日 |

**三个关键结论：**

1. 三项功能全部做成**旁路展示层**：复用现有指标与评分函数，但不把新结果回灌到 `score` / `direction` / `risk`。评分冻结的边界因此是清晰的。
2. **订单流 v1 不需要 WebSocket**。REST 采样足以支撑“主动买卖量、窗口净额、大单、盘口失衡”四类指标；WS 只解决“逐笔完整性/亚秒级延迟”，代价是新增依赖、长连接重连和代理穿透复杂度，建议延后。
3. 三项功能与预测/回验链路的衔接点统一放在一张新表 `prediction_context`，按 `prediction_id` 一对一挂载，不改 `predictions` 和 `prediction_results` 的现有字段与回验状态机。

## 3. 总体设计原则

1. **旁路**：新服务读取现有行情缓存或自行低频取数，产出独立字段；现有 `analysis`、`signal`、`predictions` 的语义不变。
2. **缓存优先**：调度任务写缓存，HTTP 接口只读缓存；接口响应时间与代理抖动解耦。
3. **采样诚实**：订单流基于 REST 轮询，必然存在漏单；响应里显式给出 `sampled`、`window_coverage_pct`、`gap_suspected`，不把采样值包装成“完整逐笔”。
4. **上下文可回验**：任何在预测时刻可见的新指标，都落到 `prediction_context`，后续可按共振等级/订单流偏向分组统计胜率。
5. **默认关闭即可回退**：新增调度任务与前端入口都用配置开关控制；关闭后行为与 2.3.0.0 一致。

## 4. 多周期（Multi-Timeframe）

### 4.1 要解决的问题

- 现在一个币种只看一个周期（15m）。15m 做多、4H 下跌时，界面仍显示“做多”，用户无法判断这是顺势还是逆势。
- 需要回答三个问题：各周期分别是什么方向？周期之间是否共振？当前主周期信号是否逆大周期？

### 4.2 v1 范围

- 固定三档：`15m`、`1H`、`4H`（已定稿），其中 `15m` 为主周期；v1 不提供档位自定义 UI，`OKE_MTF_TIMEFRAMES` 仅作开发调试用。
- 每个周期输出：方向、评分、等级、Market Regime、EMA 排列、RSI、MACD 柱、ATR 占价格比。
- 输出共振结论：`STRONG_LONG / LONG / MIXED / NEUTRAL / SHORT / STRONG_SHORT`，以及 `alignment`（与主周期同向的周期数）、`counter_trend`（主周期方向与更高周期相反）。
- **不做**：不按周期分别生成预测记录，不改变 `predictions` 的数量与节流规则，不引入多周期加权总分去替换现有评分。

### 4.3 数据与计算

| 项 | 设计 |
|---|---|
| 接口 | `GET /api/v5/market/candles?instId=...&bar=...&limit=300` |
| K 线数量 | 300 根（OKX 单次上限），足够计算 EMA120、MACD、ATR；4H × 300 ≈ 50 天 |
| bar 映射 | `15m → 15m`、`1h/1H → 1H`、`4h/4H → 4H`、`1d/1D → 1D`；统一在 `oke_client` 内做 |
| 刷新节奏 | 每 60 秒一轮，独立 `ThreadPoolExecutor(max_workers=4)`，`max_instances=1`、`coalesce=True` |
| 请求量 | 4 币种 × 3 周期 / 60s = 12 请求/分钟，对现有 5s 主循环影响可忽略 |
| 指标 | 直接调用未修改的 `indicator_service` 与 `calculate_market_score`，逐周期独立计算 |
| 方向口径 | 使用每周期**原始方向**（未经 `DirectionTracker`）；`DirectionTracker` 是按币种单状态，不能同时承载三个周期 |
| 已知近似 | OI 变化率、资金费率是币种级数据，三个周期共用同一值；这在 v1 是明确接受的近似，响应里用 `shared_inputs: true` 标注 |

共振规则（纯展示，不参与评分）：

- 取主周期（`WatchItem.timeframe`，当前 15m）方向为基准。
- 三个周期同向且无 NEUTRAL → `STRONG_LONG/STRONG_SHORT`。
- 至少两个周期同向且与主周期一致 → `LONG/SHORT`。
- 主周期与更高周期相反 → `counter_trend=true`，共振等级降为 `MIXED`，并给出原因。
- 其余 → `MIXED` 或 `NEUTRAL`。

### 4.4 存储

- 实时结果只放内存缓存，不建表。
- 预测时刻的快照写入统一的 `prediction_context`（见第 7 节），用于后续分组统计。
- 理由：多周期每秒都在变，落库价值低；真正需要沉淀的是“预测发生时”的上下文。

## 5. 风险管理（手工订单）

### 5.1 要解决的问题

- 订单只有开仓价、方向、数量、备注；没有止损/止盈，也没有“这笔交易计划亏多少、占总资金多少、组合是否过度集中”。
- 现有价格触及只检测开仓价 ±0.5%，与真实止损/止盈无关。

### 5.2 v1 范围与非目标

**做：**

- 为开仓单增加可选 `stop_loss`、`take_profit`。
- 计算并展示：止损距离、止盈距离、盈亏比 R、计划风险金额、风险占权益比、名义价值。
- 组合视图：总名义敞口、多空净敞口、按币种集中度、未设止损订单数。
- 止损/止盈触达检测与事件留档（30 分钟冷却，仅提示，不自动平仓）。
- 按权益与单笔风险比例给出建议数量（用户可忽略）。

**不做：**

- 不连接交易所下单、不读取交易所真实持仓、不自动平仓。
- v1 不做合约面值换算（`ctVal/ctMult`）；数量沿用现有“币数量”语义，名义价值 = 开仓价 × 数量，与现有 `pnl_abs` 口径一致。
- 不把止损/止盈结果写回五维评分或预测链路。

### 5.3 计算口径

设 `entry` 为开仓价，`qty` 为数量（币数量），`equity` 为配置的账户权益：

| 指标 | LONG | SHORT |
|---|---|---|
| 止损距离% | `(entry - SL) / entry × 100` | `(SL - entry) / entry × 100` |
| 止盈距离% | `(TP - entry) / entry × 100` | `(entry - TP) / entry × 100` |
| 计划风险 | `abs(entry - SL) × qty` | 同左 |
| 盈亏比 R | `abs(TP - entry) / abs(entry - SL)` | 同左 |
| 风险占权益% | `计划风险 / equity × 100` | 同左 |
| 名义价值 | `entry × qty` | 同左 |

校验规则：

- LONG：`SL < entry < TP`；SHORT：`SL > entry > TP`；只填一个时另一侧为空。
- `SL == entry`、`TP == entry`、负数量、非有限数一律拒绝（400）。
- 数量为 0 时允许保存订单，但不计算计划风险与建议数量。
- 权益未配置时，`risk_of_equity_pct` 与 `suggested_qty` 返回 `null`，并在 `warnings` 中提示“未配置账户权益，无法计算风险占比”；不内置任何假设资金量。

触发规则（只用内存最新价，不额外请求 OKX）：

- LONG：`price <= SL` → `sl_hit`；`price >= TP` → `tp_hit`。
- SHORT：`price >= SL` → `sl_hit`；`price <= TP` → `tp_hit`。
- 同一订单 + 同一事件 30 分钟冷却；事件首次触发写入 `risk_events`，同一事件在冷却期内不重复写。
- 事件只代表“价格触及”，不代表成交；响应与前端文案必须写明“仅提示”。

建议数量：

```
suggested_qty = equity × risk_per_trade_pct / 100 / abs(entry - SL)
```

结果只展示，不自动带入开单表单。

## 6. 订单流（Order Flow）

### 6.1 要解决的问题

- 现有 `cvd` 是“最近一批成交的买卖量求和”，没有 `tradeId` 去重、没有时间窗口、没有累计基线；`cvd_change` 只是两次快照求和之差，不能说明主动买卖力量。
- 没有盘口深度失衡、没有大单识别，`capital_behavior` 因缺少真实买卖量一直处于停用状态。
- 需要回答：当前窗口内主动买还是主动卖占优？盘口哪边更厚？有没有异常大单？数据是否可信？

### 6.2 数据源与采样口径

| 数据 | 接口 | 关键字段 | 限制 |
|---|---|---|---|
| 逐笔成交 | `GET /api/v5/market/trades?instId=...&limit=500` | `tradeId`、`px`、`sz`、`side`（吃单方向）、`ts` | 单次最多 500 条；高频时 5 秒内可能超过 500，必然漏单 |
| 盘口 | `GET /api/v5/market/books?instId=...&sz=400` | `bids[[px,sz,...]]`、`asks` | 深度档位有上限；不同品种盘口厚度差异大 |

采样策略：

- 默认全部关注币种统一 10 秒一轮，v1 不对持仓币种单独加速（`OKE_ORDERFLOW_INTERVAL_SECONDS=10`）；如后续实测请求余量充足，再开启持仓币种 5 秒的可选配置，默认关闭。
- 每轮按 `tradeId` 去重后并入滚动窗口（默认 5 分钟，可配 15 分钟）。
- 响应必须带质量字段：
  - `sampled=true`；
  - `trade_count`；
  - `window_coverage_pct`（有成交的秒数 / 窗口秒数）；
  - `gap_suspected`（本轮返回条数达到 500，或 `tradeId` 出现明显跳跃）。

### 6.3 指标定义

| 指标 | 定义 |
|---|---|
| 主动买量 / 卖量 | 窗口内 `side=buy` / `side=sell` 的 `sz` 求和（基础币） |
| 主动净额 delta | `buy_volume - sell_volume` |
| delta 比率 | `delta / (buy_volume + sell_volume)`，范围 -1..1 |
| 窗口 CVD | 窗口内 delta 的累计；另设 `session_cvd`，进程启动归零，响应中明确“重启归零” |
| 大单 | 名义价值 ≥ `max(固定阈值, 窗口内 p95)`；默认固定阈值 50,000 USDT；返回最近 20 笔 |
| 盘口失衡 | `(bid_depth - ask_depth) / (bid_depth + ask_depth)`，按 ±0.5% 价格带聚合；同时给 top20 档 |
| 流向偏向 `flow_bias` | 由 delta 比率、盘口失衡、大单买卖偏斜合成为 -100..+100 的展示分，纯规则 |
| 数据质量 | `sampled`、`trade_count`、`window_coverage_pct`、`gap_suspected` |

注意：`flow_bias` 只用于展示与预测上下文，不进入五维评分。

### 6.4 WebSocket 专项结论

| 问题 | 结论 |
|---|---|
| v1 是否必须 WS？ | **不必须**。REST 500 条成交 + 400 档盘口足以计算窗口聚合、盘口失衡和大单；代价是漏单，已用质量字段显式标注 |
| WS 能带来什么？ | 逐笔完整性、100ms 级 `trades` 推送、`books5`/`bbo-tbt` 亚秒级盘口；可做真正的 session CVD |
| 国内代理下是否可行？ | 技术上可行：WSS 走 HTTP CONNECT，主流本地代理（Clash/V2Ray 等）通常支持；但需要长连接心跳、断线重连、订阅恢复、代理空闲超时处理 |
| Python 实现代价 | 需新增 `websocket-client`（同步线程模型，支持代理参数）或 `websockets`（异步，v15+ 支持代理）；要补 PyInstaller `hiddenimports`，并新增独立线程/事件循环 |
| 风险 | 代理抖动会导致反复重连；现有架构是线程 + 同步 requests，引入 asyncio 会增加关闭与调度复杂度；无现成测试 |
| 建议 | **v1 先 REST 采样；WS 作为后续可选增强**。只有在确认“漏单导致指标不可用”或需要亚秒级盘口时再立项，预估额外 2–3 人日 |

## 9. 建议落地顺序与验收标准

### 9.1 顺序

```
风险管理（本地数据，零新增外部请求，最快可用）
   ↓
多周期（新增低频外部请求，先补 bar/limit，再做展示）
   ↓
订单流 REST 采样（新增数据语义与限频约束，最需要实测）
   ↓
prediction_context + 绩效分桶（等前三项稳定、样本开始积累后）
```

理由：

- 风险管理依赖最少，直接改善现有订单页，适合作为第一项验证“旁路不改评分”的边界。
- 多周期比订单流确定：接口简单、指标复用现有函数，主要风险在 bar 规范化和限频。
- 订单流的“采样不完整”是产品语义问题，需要先跑起来观察漏单率，再决定是否上 WS。
- 上下文与绩效分桶必须等前三项产出稳定字段，否则表结构会反复改。

### 9.2 验收标准

**风险管理**

- LONG/SHORT 两个方向的 SL/TP 校验全部通过；非法组合返回 400。
- 价格跨越 SL/TP 时，`risk_events` 新增一条；30 分钟内同一订单同一事件不重复写。
- 组合接口的总名义、净敞口、计划风险、集中度与手工计算一致。
- 重启后订单的 SL/TP 与风险设置仍存在。

**多周期**

- 四个关注币种均能返回 3 个周期；单个周期失败时其余周期仍可用。
- `counter_trend` 在主周期与 4H 相反时为 `true`，同向时为 `false`。
- 关闭 MTF 调度后，现有 `/api/analysis`、`/api/monitor/snapshot` 行为与改动前一致。

**订单流**

- 同一 `tradeId` 不重复计入；本轮 500 条时 `gap_suspected=true`。
- 主动买/卖量、delta、盘口失衡与交易所页面方向一致（人工抽查）。
- GET 接口不产生 OKX 请求；断网时返回上一轮缓存并标记 `stale`。
- 采样表按配置间隔写入，不出现每 5 秒一行。

**预测上下文**

- 每条新预测最多一行上下文；上下文为空不影响预测与回验。
- 分组统计能按 `mtf_resonance`、`orderflow_bias` 返回胜率；样本 < 30 时明确提示。
